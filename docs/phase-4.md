# Phase 4 Review：管理员赛事管理与成绩发布

状态：已通过用户Review，最终发布确认及409冲突提示已完成针对性核验。冲突后必须成功刷新、重新核对再手动提交，刷新失败仍保持提交锁定。未进入Phase 5，未正式部署，未迁移或修改用户真实赛事库及旧站数据。

## 已实现

- `/manage`沿用蓝白移动端布局，管理员可选择队伍、赛程、成绩发布、设置；原记分台通过“记分与成绩修正”进入。普通用户及记分员不能使用管理接口。
- 空库先配置管理员访问码，登录后选择8队/10队生成固定模板；录入固定抽签编号对应的实际队名，保存并一次确认发布正式小组赛程。无清空、删除比赛或重复初始化入口；开赛后保留规模、编号、分组锁定及队名修正。
- 两片场地分别查看完整赛程；未开始比赛可改场地或插入场内顺序，其后未开始场次顺延，已开始/结束比赛的位置、实际对阵和比分不变。不增加开赛时刻、网高提示或跨场地冲突检测。原有每场地最多一场LIVE限制保留。
- 小组全部提交后预览排名和交叉对阵；全部指标仍相同的队伍只能在当前并列组内排序，填写裁定依据，随后确认公布。公开排名使用确认快照展示人工裁定结果，原非递归算法不变。
- 沿用成绩修正、Approval、AuditLog及版本机制。小组成绩修正后原交叉/最终确认失效；未开始对阵隐藏待重确认，真实开打/完赛对阵和比分保留，存在排名差异时要求核对后确认保留。
- 半决赛胜负继续联动未开始的决赛、季军赛；修正半决赛不改已开打后续比赛，最终公布前需核对该差异。全部正式比赛完成且名次完整、无重复后，管理员预览并确认公布第1～8/10名。任何正式结果修正使旧最终确认失效。
- 修改赛事名称、地点、分段规则、简短公告；公告留空即撤回。重置管理员/两片场地访问码采用原散列及凭据版本机制，旧码和旧会话失效；新码仅在本次受保护响应显示，不入日志。管理员重置自己后重新登录。
- 管理页手动刷新，发布时服务端重算并检查配置/成绩版本；刷新后清除过期裁定草稿，未保存的队名不能直接发布。重新登录可正常重新加载管理数据。

此前两项展示调整已存在：进行中BO3交叉卡片保留总局分与当前局分；紧凑比赛卡片长队名最多两行，详情完整展示。本阶段未改公开页布局或记分台加减分按钮。

## 接口与数据保护

- `GET /api/manage/tournament`：仅管理员；返回配置、固定队伍/赛程、比赛版本、排名/最终名次预览、确认状态和凭据配置状态，绝不返回散列或已有访问码。
- `POST /api/manage/tournament`：仅管理员且同源；请求为`{ expectedRevision, action }`，空库初始化时版本为`null`。命令包括`INITIALIZE`、`TEAMS`、`CONFIG`、`PUBLISH_SCHEDULE`、`MOVE_MATCH`、`CONFIRM_CROSS`、`CONFIRM_FINAL`、`RESET_CODE`，严格拒绝额外字段。
- 调整场次另核对比赛版本；交叉/最终确认另核对对应成绩版本；重置另核对凭据版本。竞争提交只有一方生效，过期操作返回409，不新增第二套发布表。
- 新迁移仅使管理员凭据可在赛事创建前存在，初始化时关联到本赛事。记分员仍必须关联有效赛事及场地。迁移复制保留原凭据ID、散列和版本，不改比赛、比分、日志或历史迁移。
- 已有工程升级：停止服务、备份独立数据库后执行一次`npm run db:migrate`，再`npm run dev`。空库初始化与日常启动的具体步骤见根目录README。
